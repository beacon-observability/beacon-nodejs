## Public Package Acceptance

A new application directory and empty npm cache installed all three exact `1.3.0` versions exclusively from the public npm registry, with no local tarballs or repository packages.

On Node.js 24.16.0:

- The installed product exports exactly `HttpProfilingExporter`, `NodeProfiling`, and `startProfilingFromEnv`.
- The public register entry ran an unchanged application and exported traces plus compatible pprof profiles to local receivers.
- Five installed-package occurrence tests verified per-request IDs, current trace context, capacity behavior and real OTLP HTTP delivery, with ANSI SQL analysis both absent and enabled.
- A real Express query-to-file-read application ran through the ESM preload. Default configuration exported no Security events or runtime helper. Explicit enablement exported three findings with one finding ID, three occurrence/evidence IDs and current trace IDs, counts `1, 2, 3`, and full-evidence sampling `true, false, false`.
- Runtime SBOM and compatible pprof reached the receiver. Security local output remained absent in both modes.

## Limits and Rollback

Security requires Node.js 22.22.3+ or 24.11.1+ and an explicit include selector. Use the ESM `--import @beacon-observability/nodejs/register` preload for Security; CommonJS `--require` initializes tracing and profiling only.

Attack evidence is independent of candidate code risk, assessment and exploit outcome. Unsupported syntax, imprecise ranges, work-budget exhaustion and missing policy remain unknown. Counters are process-local, delivery is bounded best effort, and a trace ID does not guarantee trace retention. SQL analysis requires explicit ANSI configuration.

This is local protocol acceptance, not a new DataKit backend qualification. Profiling uses compatible pprof rather than the OpenTelemetry Profiles signal. Local output remains diagnostic and opt-in.

Rollback: pin all three Beacon packages to `1.2.0` in a clean application. Published packages and source tags are immutable.
